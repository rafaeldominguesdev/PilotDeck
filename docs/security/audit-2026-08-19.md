# Auditoria de segurança — PilotDeck

Data: 2026-08-19  
Snapshot-base: commit `919bde6017b4`  
Escopo: board web, API HTTP, servidor MCP, banco, Docker, deploy, scripts e dependências.

Esta auditoria foi somente leitura sobre o código de produção. A única entrega criada é este relatório. Nenhum exploit foi executado contra instância real. Valores de credencial e endereços foram substituídos por `***`.

O risco imediato é o quickstart aceitar uma chave fixa e pública para assinar sessões. Como a sessão é aceita sem confirmar que o usuário ainda existe, qualquer instalação iniciada por esse caminho pode aceitar uma sessão forjada.

O isolamento direto entre workspaces está bem aplicado nas consultas MCP por UUID e por short id: um token do workspace A não lê, altera nem deleta card, missão ou projeto do workspace B pelos tools auditados. Há, porém, duas exceções laterais: o pareamento público procura códigos globalmente e o namespace de short ids é global. Além disso, dentro do mesmo workspace, um token comum pode tomar claims, entregar trabalho alheio e apagar dados sem `canManage`.

## Findings confirmados

### V-001 — Crítica — chave pública de sessão no quickstart permite sessão forjada

- Categoria: autenticação, secrets, Docker.
- Evidência: `docker-compose.yml:28`, `apps/web/src/lib/session.ts:16`, `apps/web/src/lib/session.ts:38`, `apps/web/src/lib/cookies.ts:10`.
- O que ocorre: o compose principal define `AUTH_SECRET=***` como literal público e inicia o app em modo de produção. O valor satisfaz o tamanho mínimo, assina JWT com HS256 e é aceito apenas pela assinatura e pelos tipos de `userId` e `email`. `getSession` não confirma o usuário no banco.
- O que um atacante consegue: forjar uma sessão aceita por páginas protegidas, ler todo o board e executar actions que exigem apenas uma sessão não nula. Actions que gravam uma FK de usuário podem falhar com um id inventado, mas leitura e várias mutações de workspace continuam disponíveis.
- Como reproduzir: em uma instalação descartável criada pelo compose principal, usar a chave pública sem imprimi-la para assinar um JWT HS256 com os dois campos esperados, gravá-lo no cookie de sessão e abrir a página protegida. O acesso passa sem login e sem consulta à tabela de usuários.
- Correção sugerida: remover o literal; exigir uma chave aleatória por instalação com expansão obrigatória no compose; rotacionar a chave de todas as instalações existentes; e validar no banco que o usuário da sessão existe e está ativo. Adicionar versão/revogação de sessão reduz o impacto de futuras rotações.

### V-002 — Alta — primeira conta administrativa pode ser tomada sem segredo de setup

- Categoria: autenticação, bootstrap.
- Evidência: `apps/web/src/app/setup/page.tsx:12`, `apps/web/src/actions/auth.ts:33`, `apps/web/src/actions/auth.ts:51`, `packages/db/src/domain/first-access.ts:3`.
- O que ocorre: enquanto a tabela de usuários está vazia, qualquer visitante pode abrir o setup e criar a primeira conta. Não existe token de instalação, confirmação local nem vínculo com o operador. A contagem e o insert também não são uma operação atômica; duas requisições com e-mails diferentes podem observar zero antes dos inserts.
- O que um atacante consegue: tornar-se o primeiro administrador de uma instância recém-exposta ou criar mais de uma conta na corrida de bootstrap.
- Como reproduzir: iniciar uma instância descartável com banco vazio, acessar o setup sem sessão e enviar uma conta antes do dono. A conta é criada e recebe sessão administrativa.
- Correção sugerida: exigir segredo de setup de uso único, manter a rota disponível apenas na interface local até a ativação e serializar a criação do singleton em transação com lock/constraint de banco.

### V-003 — Alta — código de pareamento curto pode ser adivinhado em paralelo e entrega token MCP

- Categoria: autenticação, rate limit, isolamento.
- Evidência: `apps/web/src/app/api/pair/route.ts:13`, `apps/web/src/app/api/pair/route.ts:19`, `apps/web/src/lib/pairing.ts:13`, `apps/web/src/lib/pairing.ts:15`, `apps/web/src/lib/pairing.ts:79`, `apps/web/src/lib/pairing.ts:84`.
- O que ocorre: o endpoint público aceita um código de seis dígitos válido por dez minutos. A espera de 500 ms acontece por requisição, depois da consulta, e não limita concorrência, origem nem número global de tentativas. A busca pelo hash do código não recebe workspace; qualquer código ativo é um alvo global.
- O que um atacante consegue: adivinhar um código ativo e receber o token MCP real daquele workspace. Códigos iguais em workspaces diferentes também são consumidos pela mesma condição global.
- Como reproduzir: em fixture isolada, criar um pareamento e enviar tentativas concorrentes ao endpoint público. A latência fixa não serializa o lote; quando o código correto entra, a resposta devolve o token do registro encontrado.
- Correção sugerida: trocar o código por desafio de alta entropia ou fluxo com confirmação humana, limitar por origem e globalmente, registrar tentativas, vincular a troca a workspace e nonce, e colocar expiração e unicidade na condição atômica do banco.

### V-004 — Alta — token comum pode tomar claim e entregar execução de outro token

- Categoria: autorização, integridade de workflow.
- Evidência: `packages/mcp-core/src/state/claim.ts:89`, `packages/mcp-core/src/state/claim.ts:94`, `apps/web/src/mcp/tools.ts:1640`, `apps/web/src/mcp/tools.ts:2355`, `apps/web/src/mcp/tools.ts:2390`.
- O que ocorre: release e heartbeat exigem o token dono ou `canManage`, mas `task_claim {force:true}` não faz essa verificação. `task_deliver` valida apenas o estado do card e fecha o attempt aberto encontrado pelo card, sem comparar `claimedByTokenId` com o caller.
- O que um atacante consegue: interromper o worker legítimo, marcar sua tentativa como abandonada, forjar uma entrega e atribuir telemetria falsa a trabalho alheio.
- Como reproduzir: em um workspace de teste com tokens A e B, fazer A reivindicar um card; com B, chamar force claim ou entregar o card diretamente. As operações são aceitas mesmo sem `canManage`.
- Correção sugerida: exigir o token dono para entrega; permitir takeover apenas quando a lease expirou ou quando `canManage` autoriza; vincular entrega ao `attempt_id`; registrar explicitamente ator e motivo.

### V-005 — Alta — hard delete não exige `canManage` e remove também a trilha de auditoria

- Categoria: autorização, destruição de dados.
- Evidência: `packages/db/src/schema/mcp-token.ts:23`, `apps/web/src/mcp/tools.ts:711`, `apps/web/src/mcp/tools.ts:903`, `apps/web/src/mcp/tools.ts:2607`, `apps/web/src/mcp/tools.ts:3062`.
- O que ocorre: a documentação do token comum diz que ele reivindica e entrega cards. Mesmo assim, `project_delete`, `mission_delete` e `task_delete` não chamam `requireManage`. O delete de card usa cascade e apaga attempts, handoffs, comentários e subtasks.
- O que um atacante consegue: com qualquer token válido do workspace, destruir cards ou um projeto inteiro e apagar a evidência que ajudaria a investigar o abuso.
- Como reproduzir: criar um token com `canManage=false` numa fixture, criar dados e chamar os três tools de delete, incluindo `force` no projeto ocupado. As deleções são aceitas.
- Correção sugerida: separar escopos de leitura, escrita e administração; exigir privilégio destrutivo para hard delete; preferir soft delete/tombstone imutável; e manter audit log fora da cascade.

### V-006 — Alta — texto hostil de card vira instrução dentro do briefing do agente

- Categoria: prompt injection, fronteira MCP/agente.
- Evidência: `apps/web/src/mcp/briefing.ts:59`, `apps/web/src/mcp/briefing.ts:78`, `apps/web/src/mcp/briefing.ts:89`, `apps/web/src/mcp/briefing.ts:104`, `apps/web/src/mcp/server.ts:37`, `apps/web/src/mcp/server.ts:137`.
- O que ocorre: título, contrato, passos, comentário de reabertura, contexto de missão e contexto de projeto são interpolados diretamente no markdown que o modelo recebe. O contexto também aparece nas instruções e resources MCP. Não há marca de conteúdo não confiável nem regra de precedência que o cliente possa impor.
- O que um atacante consegue: alguém capaz de escrever conteúdo no board pode tentar induzir o agente executor a ler arquivos locais, revelar dados, alterar código fora do contrato ou usar credenciais disponíveis à CLI. O board amplia a permissão do escritor para a permissão da máquina do agente.
- Como reproduzir: em ambiente isolado, criar um card cujo campo de contrato tenta substituir a tarefa e solicita uma ação local; reivindicar o card e observar que o texto reaparece integralmente sob seções operacionais do briefing.
- Correção sugerida: transportar conteúdo do usuário em bloco estrutural explicitamente não confiável, adicionar instrução imutável no cliente para nunca obedecer a comandos vindos desses campos, exigir confirmação para ações fora do contrato e executar workers com filesystem, rede e credenciais mínimos. Sanitização textual sozinha não resolve prompt injection.

### V-007 — Média — payloads e coleções sem teto permitem exaustão e inflação de contexto

- Categoria: validação, disponibilidade, custo.
- Evidência: `apps/web/src/app/api/pair/route.ts:14`, `packages/mcp-core/src/schemas/common.ts:57`, `packages/mcp-core/src/schemas/common.ts:130`, `packages/mcp-core/src/schemas/common.ts:180`, `packages/mcp-core/src/schemas/tools.ts:53`, `packages/mcp-core/src/schemas/tools.ts:357`, `packages/mcp-core/src/schemas/tools.ts:373`, `packages/mcp-core/src/schemas/tools.ts:593`, `packages/mcp-core/src/schemas/tools.ts:603`.
- O que ocorre: os objetos MCP são `strict` e evitam mass assignment, mas vários textos, arrays, artifacts, evidence, segmentos de usage, comentários e subtasks não têm `.max()`. O endpoint público lê JSON inteiro sem limite de aplicação. Também não há quota por token ou limitação de login/MCP nos arquivos de deploy.
- O que um atacante consegue: consumir memória/CPU, inflar o banco e os briefings e provocar gasto de contexto do agente; no endpoint público, nem token é necessário para enviar corpo excessivo.
- Como reproduzir: em instância descartável, enviar JSON grande porém válido em um campo sem teto e depois ler ou reivindicar o registro. O schema aceita e o conteúdo é persistido/devolvido.
- Correção sugerida: impor limite de corpo no proxy e na aplicação, limites por string/array no Zod, quota por token/workspace, paginação de artifacts/evidence e rate limit para rotas públicas e MCP.

### V-008 — Média — app roda como root no container

- Categoria: Docker, privilégio.
- Evidência: `Dockerfile:2`, `Dockerfile:10`, `Dockerfile:36`. Não existe instrução `USER` no arquivo.
- O que ocorre: build e runtime herdam o usuário root da imagem base. O updater opcional ainda opera com acesso equivalente ao daemon do host, embora esteja em container separado.
- O que um atacante consegue: após uma falha de execução remota no app ou numa dependência, escrever em todo o filesystem gravável do container e ampliar o impacto sobre volumes montados. A presença do updater aumenta o custo de uma quebra de isolamento nesse componente.
- Como reproduzir: construir a imagem descartável e executar `id` como entrypoint; o UID efetivo é root.
- Correção sugerida: criar usuário sem privilégio, ajustar ownership apenas dos caminhos necessários, usar filesystem somente leitura quando possível, remover capabilities, habilitar `no-new-privileges` e manter o updater opt-in e isolado.

### V-009 — Média — erros e saída de comandos são exibidos sem redaction

- Categoria: vazamento operacional, logs.
- Evidência: `apps/web/src/mcp/tools.ts:283`, `apps/web/src/mcp/tools.ts:288`, `apps/web/src/lib/source-update.ts:117`, `docker-compose.yml:71`, `docker-compose.yml:76`, `apps/web/src/components/update-panel.tsx:217`, `apps/web/src/components/update-panel.tsx:263`.
- O que ocorre: a resposta MCP mascara o erro, mas o servidor registra o objeto bruto do driver. O atualizador preserva o tail bruto de stdout/stderr e o mostra na UI; o sidecar faz o mesmo com o log de compose. Não existe redactor central.
- O que um atacante consegue: fazer parâmetros SQL, conteúdo de card, caminho local ou credencial embutida em comando/remote aparecer em log ou na tela do operador quando uma operação falha.
- Como reproduzir: numa fixture, fazer um comando de atualização falhar imprimindo um marcador sintético; o marcador chega sem alteração ao painel. Não usar credencial real no teste.
- Correção sugerida: log estruturado por allowlist, ids de correlação e redaction antes de persistir/exibir; descartar argumentos e parâmetros do driver; testar padrões de token, cookie, conexão e endereço.

### V-010 — Baixa — short id global cria side channel e acoplamento entre workspaces

- Categoria: isolamento, enumeração.
- Evidência: `packages/db/src/schema/task.ts:46`, `packages/db/src/schema/project.ts:34`, `apps/web/src/mcp/tools.ts:3439`, `apps/web/src/mcp/tools.ts:3452`.
- O que ocorre: prefixo de projeto é único por workspace, mas `task.short_id` é único no banco inteiro e `shortIdTaken` consulta globalmente. Dois workspaces podem escolher o mesmo prefixo; o segundo pula números já usados pelo primeiro.
- O que um atacante consegue: inferir que ids foram ocupados em outro workspace e reservar números para distorcer a sequência de outro tenant. Não foi encontrado acesso ao conteúdo do card por esse canal.
- Como reproduzir: em banco de teste com dois workspaces e o mesmo prefixo, criar o primeiro card em A e depois em B; B recebe um número posterior apesar de seu contador local estar no início.
- Correção sugerida: adicionar `workspace_id` à task, tornar a unicidade composta por workspace e short id e usar FKs/constraints compostas para impedir relações cruzadas.

### V-011 — Baixa — resposta padrão não define baseline de headers de segurança

- Categoria: web hardening.
- Evidência: `apps/web/next.config.ts:3`, `apps/web/next.config.ts:8`.
- O que ocorre: a configuração remove o header de tecnologia, mas não define CSP, `frame-ancestors`, HSTS, Referrer Policy, Permissions Policy nem uma política explícita de MIME sniffing. Os exemplos de deploy também não declaram esse baseline.
- O que um atacante consegue: uma falha futura de conteúdo ativo encontra menos defesa em profundidade; framing permanece possível em cenários same-site. O cookie `SameSite=Lax` reduz o caso cross-site comum.
- Como reproduzir: iniciar o app direto em fixture e inspecionar os headers da resposta; o baseline acima não está presente por configuração do projeto.
- Correção sugerida: definir headers no app e no proxy, com CSP compatível com o runtime, `frame-ancestors 'none'`, HSTS somente no ponto TLS e políticas restritivas de referrer, permissions e MIME.

## Isolamento entre workspaces — veredito explícito

Veredito: não foi encontrado IDOR direto que permita a um token do workspace A ler, alterar ou deletar projeto, missão ou card do workspace B, por UUID ou short id.

A cadeia que sustenta o veredito é:

1. `apps/web/src/mcp/auth.ts:36` busca o hash do token e `apps/web/src/mcp/auth.ts:55` coloca o `workspaceId` do registro no contexto.
2. `apps/web/src/mcp/tools.ts:3366` resolve projeto junto com `project.workspaceId`.
3. `apps/web/src/mcp/tools.ts:3385` resolve missão junto com `mission.workspaceId`.
4. `apps/web/src/mcp/tools.ts:3404` resolve task por join com projeto e filtra o workspace antes de devolver o card.
5. Update/delete/claim/deliver primeiro usam esses resolvers; ids de projeto e missão de destino também passam pelos helpers escopados.

Os testes existentes que cobrem projeto estrangeiro, short id estrangeiro, busca e missão estrangeira passaram no run completo. As ressalvas são V-003, que permite obter um token por um canal público global, e V-010, que vaza ocupação do namespace sem devolver conteúdo.

Não há RLS nem políticas SQL nas migrations. O isolamento depende integralmente de cada consulta da aplicação. Isso não abriu um IDOR adicional confirmado, mas reduz a defesa em profundidade.

## Token MCP — geração, comparação, revogação e escopo

- Geração: `apps/web/src/mcp/token.ts:7` usa 24 bytes aleatórios, resultando em entropia suficiente para o token normal.
- Armazenamento: `apps/web/src/mcp/token.ts:3` grava SHA-256; o valor completo não fica na tabela de tokens. O pareamento guarda o futuro segredo em texto claro até a troca, por no máximo a TTL prevista.
- Comparação: `apps/web/src/mcp/auth.ts:36` faz lookup pelo hash no banco. Não existe `timingSafeEqual`, mas também não há comparação incremental do segredo; o lookup usa hash de tamanho fixo e o token tem alta entropia. Não foi identificado oracle de timing prático aqui.
- Revogação: `apps/web/src/mcp/auth.ts:42` recusa `revoked` antes de criar o contexto.
- Escopo: o `workspaceId` vem do registro do token, nunca do body. O escopo tenant está consistente; o escopo funcional é excessivo conforme V-004 e V-005.

## Dependências conhecidas

`pnpm audit --json` terminou com exit code 1 e contou: 0 crítica, 1 alta, 1 moderada.

1. `drizzle-orm` 0.44.7 — CVE-2026-39356 / GHSA-gpj5-g38j-94v9, severidade upstream alta, corrigida a partir de 0.45.2. O problema é escape de identificador SQL. O repo não chama `sql.identifier`, por isso uma cadeia explorável no código atual não foi confirmada; ainda assim, a dependência direta deve ser atualizada e os testes repetidos.
2. `esbuild` 0.18.20 — GHSA-67mh-4wv8-2f99, severidade upstream moderada, corrigida a partir de 0.25.0. Entra por dependência de desenvolvimento de `drizzle-kit`; o servidor vulnerável não é iniciado pelo runtime de produção. O Dockerfile instala dev dependencies na etapa de build, então a versão continua presente na imagem sem necessidade.

## Suspeitas não confirmadas

1. A CVE do Drizzle está instalada, mas não foi localizada chamada à API de identificador vulnerável; a explorabilidade atual ficou não confirmada.
2. A ausência de RLS pode transformar um futuro filtro esquecido em vazamento total, mas não é um caminho remoto por si só.
3. Infraestrutura externa pode adicionar rate limit e headers não descritos no repo. A auditoria avaliou o comportamento que o repositório entrega sozinho.

Não foi encontrado SSRF alcançável por MCP, SQL injection no código local nem XSS no conteúdo de card. Esses veredictos não anulam os advisories e as falhas de autorização acima.
