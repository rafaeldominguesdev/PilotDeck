chapter 06 of 08 · from the terminal

Say the outcome, let the board carry the context

You do not need to describe the work twice. The card already holds the contract, the harness, the mission and the branch convention, and the agent reads all of it on claim. Your prompts get to be short and about intent.

01 · the four patterns

What you actually say all day

Grab the next task

say this grab the next task from the board

The agent lists the queue, claims one card, and gets the briefing. Narrow it when you care which: "grab the next open bug in AGB", "claim AGB-12 and work it".

Register this as a task

say this register this as a task for later: the insights page has no empty state for a workspace with zero attempts. write what, why and how to confirm.

Discoveries become cards while the context is fresh. This is the single habit that keeps a chat log from becoming the real backlog.

What is the policy

say this what is the harness policy on this board, and what does it recommend for a bug?

Useful before you delegate something expensive, and useful to catch a policy line that drifted after someone edited the executors.

What did it cost

say this how much did the launch mission cost so far, per model?

The agent queries the same aggregation the Insights page runs, so the number it tells you and the number on the screen cannot disagree. Chapter 7 goes deeper.

02 · what makes a prompt work

Three habits, one anti-pattern

  • Name the card by its short id. "Work AGB-14" is unambiguous; "the login thing" costs a search and sometimes finds the wrong card.
  • Ask for the tool when the agent wanders. Most agents pick the right tool, but "use task_list on pilotdeck" ends a confusion immediately.
  • Say when the work is done. "Deliver it when the three suites pass" gives the agent a finish line it can check itself.
  • Do not paste the card into the chat. Re-describing the contract in the prompt creates a second version of the truth. If the card is wrong, fix the card.
03 · the executor contract

Every briefing ends the same way

The last thing an agent reads in a briefing is the executor contract: when done, call task_deliver with a summary, evidence, the branch, and a usage block of tokens, duration, cost and turns. If the harness cannot read exact numbers, the instruction is to estimate and mark them estimated, because an estimate beats silence.

You will occasionally meet an agent that delivers without usage. The card still lands, the board flags it, and you can ask for the numbers afterwards: they can be written onto the attempt after the fact.

say this you delivered AGB-14 without usage. estimate the tokens, turns and cost for that run and update the card, marked as estimated.
04 · long runs

Keep the board in sync while the work is long

A claim moves the card to In progress and stamps the executor on it, which is already most of what a status update is for. For work spanning hours, two things keep the board honest:

  • Register the branch as soon as it exists, so the card and the code point at each other before the delivery.
  • Post a note when a plan changes rather than silently redefining the card. If the change is real scope, it is a new card.
say this register the branch agb-14-normalize-email on the card, then keep going
05 · a daily shape

Board in the morning, terminal all day

  • Morning, on the board: write cards. Contracts, with the harness pre-filled from your policy.
  • All day, in the terminal: "grab the next task", "register this as a task". Agents file their own discoveries as cards.
  • End of day, on the board: the Done column is your review queue. Validate or reopen, as in chapter 5.

Chapter checklist

  • You can start work with one sentence and no pasted context
  • Discoveries become cards in the moment, from the terminal
  • Cards are named by short id when you delegate
  • Your agents deliver with usage, estimated when they must
  • Branches are registered on their cards
  • The chat log is not where your backlog lives
