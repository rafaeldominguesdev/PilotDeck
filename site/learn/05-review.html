chapter 05 of 08 · review discipline

Done is not validated

Done means an agent believes it finished and produced evidence. Validated means a human ran the script and agrees. Only a person can make that second move, and the entire quality of the loop lives in whether you actually make it.

01 · what a delivery contains

Read the handoff before the diff

A delivered card carries a summary, evidence (commands run, files touched, links), the branch or pull request, and usage. Optionally it carries a how to verify line: a URL, a command or a screenshot reference, shown at the top of the validation panel under "For checking, open". Start there, not in the code: if the delivery cannot tell you how to check it, that is already a finding.

02 · the move

Run your own script

The validation panel lists the How to confirm steps you wrote when you created the card. Tick them as you run them. Two outcomes:

  • Validate · the card moves to Validated. Ticks are recorded with who checked what and when. A fresh delivery on the same card clears them, so nobody inherits someone else's confidence.
  • Reopen with a comment · the card returns to Open, and your comment travels to the agent inside its next claim. It reads what was wrong before it starts, in the same briefing that carries the contract.

You can validate anyway when a step no longer applies. It is an explicit button with the ticks left as they are, so an incomplete check is visible rather than silently skipped.

03 · reopen comments

Write the comment for the agent, not about it

a comment that wastes a run

"Not working."

"This is wrong, please redo it properly."

"You misunderstood the card."

a comment that fixes the run

"Step 3 fails: JOSÉ@dominio.com.br still returns 401. Normalization looks like it happens after the lookup, not before."

"The three suites pass but the count dropped by two: two tests were deleted rather than updated. Restore them against the new behavior."

The good comments name the step that failed and what you observed. That is the same rigor the card asked of you at creation time, and it turns a second attempt into a targeted fix instead of a fresh guess.

04 · the queue

Done is a queue, not a graveyard

Cards route back to a reviewer when they are delivered: a specific human, another agent, or the workspace queue. Filter the board by awaiting my review and work that list once a day. The habit that keeps the loop honest is simple: a card in Done for a week is not done, it is unvalidated work someone is already building on.

Agents can read the queue too. An orchestrator that asks for cards awaiting review can chase evidence, re-run a check, or report what is blocking, without ever stamping the validation itself.

05 · telemetry honesty

What the footer is telling you

The card footer never shows nothing. The board falls back in a fixed order: full usage; usage the executor marked as estimated; and, when the agent reported nothing at all, the duration the server measured itself from claim to deliver, with usage not reported next to it.

Read those labels during review. A card marked "usage not reported" is not a catastrophe, but it does mean the cost numbers in chapter 7 are missing that run. Real numbers found later can still be written onto the attempt.

Chapter checklist

  • Nobody but a human moves a card to Validated
  • Review starts from the handoff and the how-to-verify line, then the code
  • Each How to confirm step is ticked as it is actually run
  • Reopen comments name the failing step and what you observed
  • The Done column is worked at least once a day
  • Cards labeled estimated or usage not reported are noticed, not ignored
