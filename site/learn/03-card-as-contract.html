chapter 03 of 08 · the card is the contract

Write the test before the work

A card has three fields for a reason. What is the change, Why is the judgment the agent needs when reality does not match the plan, and How to confirm is the script you will run at review time. Write the third one first and the other two get sharper.

01 · the three fields

What each field is actually for

FieldIts jobFailure when it is weak
What The observable change. Screens, behaviors, endpoints, the shape of the output. The agent invents a scope. You get a refactor you did not ask for.
Why The reason the change matters, so the executor can make the small calls itself. Every ambiguity becomes a question, or worse, a silent guess.
How to confirm Plain-language steps with expected results. This is the review script. Review becomes a vibe. Nobody can say whether it is done.

The briefing an agent receives is exactly this contract plus the harness, the mission context and the branch convention. Nothing else is sent, so anything you leave out is genuinely missing.

02 · side by side

The same request, twice

weak card
what

Fix the login bug.

why

Users are complaining.

how to confirm

Login works.

card that executes
what

Sign-in fails for e-mails with accented characters (josé@dominio.com.br). Normalize the address before the lookup, keep the stored value untouched.

why

Roughly a fifth of our Brazilian users have an accent in the address. They cannot sign in at all, and support has no workaround to offer.

how to confirm

1. Create a user with josé@dominio.com.br → account created.
2. Sign in with the same address → session starts.
3. Sign in with JOSÉ@dominio.com.br → session starts.
4. Existing unaccented accounts still sign in → unchanged.

The good card is not longer for the sake of it. Every extra sentence removes a decision the agent would otherwise make alone, and step 4 is what stops the fix from breaking everyone else.

03 · how to confirm

Steps someone else can run

A confirmation step has an action and an expected result. It should be runnable by a person who did not write the code and did not watch the work happen: that is the whole point, because at review time you will have forgotten the context.

not a step

"Test the endpoint."

"Make sure performance is fine."

"Check that nothing broke."

a step

"POST /api/pair with an expired code → 400 and the body names the expiry."

"Open the board with 200 cards → the list paints in under a second on a cold reload."

"Run the three test suites → all green, and the count is not lower than before."

When a step needs an artifact, say so in the step. The agent can attach a link, a command or a screenshot reference to its delivery, and the board shows it at the top of the validation panel under For checking, open.

04 · size

One card, one deliverable

A card should be finishable in one execution, by one agent, with one branch. If the How to confirm needs more than about six steps, or the steps belong to different screens, you are holding two cards. Split them: the board carries the relationship, and two small deliveries review faster than one large one.

Big, undecided work is not a card yet. Make it an rfc card whose deliverable is a document; approving that document spawns the execution cards, and the trail from decision to code stays intact. Chapter 8 covers that pattern.

05 · let the agent file cards

Discoveries belong on the board, not in a chat

Agents create cards over MCP too. When something surfaces mid-work that is not this card's job, the honest move is a new card rather than scope creep.

say this to your agent register this as a task for later: the pairing endpoint has no rate limit. what, why and how to confirm, and file it in the current project.

The card it creates is subject to the same contract. If your agent writes a vague one, tell it what is missing once; most of them keep the shape afterwards.

Chapter checklist

  • Every card answers What, Why and How to confirm
  • How to confirm has numbered steps, each with an expected result
  • A person who did not do the work could run those steps
  • One card produces one deliverable on one branch
  • Undecided work is an rfc card, not a big feature card
  • Discoveries during execution become new cards instead of extra scope
