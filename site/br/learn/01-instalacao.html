capítulo 01 de 08 · instalação e primeira execução

Dois comandos e o board é seu

Nada aqui chama para fora da sua máquina. O Postgres vem no compose, a conta admin vive no seu próprio banco e o board nunca liga para casa: sem analytics, sem e-mail de verificação, sem telemetria.

01 · o que você precisa

Requisitos

Docker e Docker Compose, e um agente de código com MCP na mesma máquina em que você trabalha: Claude Code, Codex CLI, Gemini CLI, Overclock ou qualquer cliente MCP. É a lista inteira. Não existe conta para criar em lugar nenhum, nem plano na nuvem.

  • macOS: brew install --cask docker && open -a Docker (OrbStack também serve)
  • Linux: o docker da sua distro mais o pacote docker-compose-plugin
  • Windows: Docker Desktop com backend WSL2
02 · suba

Clone e levante

$ git clone https://github.com/rafaeldominguesdev/pilotdeck && cd pilotdeck $ docker compose up --build # → http://localhost:3000

O primeiro build leva alguns minutos; depois disso são segundos. Quando o log acalmar, abra http://localhost:3000.

Vai expor num servidor? Defina AUTH_SECRET com um valor seu de 32 caracteres ou mais no ambiente do compose antes que outra pessoa alcance a URL. O padrão é só para uso local. De qualquer forma, nada no app chama para fora do seu servidor.
03 · sua conta

Crie a conta admin

O primeiro acesso mostra a tela de setup: e-mail e senha, com hash no seu próprio Postgres. Sem e-mail de confirmação, sem perguntas de marketing, sem terceiro. É um login, e ele existe para que uma sessão de navegador prove que é você antes de validar o trabalho de um agente.

04 · onboarding

Três passos e o board está vivo

Passo 1 · Projeto

Dê um nome e, se quiser, cole a URL do repositório. O board deriva um prefixo de ID a partir do nome (PilotDeck vira AB), e esse prefixo comanda toda a convenção do Git: os cards nascem como AB-1, as branches como ab-1-corrige-login, e commits e pull requests carregam o mesmo id. Um projeto corresponde a um repositório; dá para adicionar mais depois.

Passo 2 · Executores

Marque as CLIs e os modelos que o seu time realmente tem. Isso não é lista de desejos: é o que o board pode recomendar. Um modelo que ninguém possui nunca vai aparecer num card. O capítulo 4 transforma essa lista em política.

Passo 3 · Conecte seu agente

São dois caminhos, os dois terminando com um agente conectado via MCP. O recomendado é o código de pareamento, e ele é o capítulo 2. Termine o wizard mesmo que pare por aqui: o board já está usável, e as Configurações têm os mesmos botões.

05 · o que você deve ver

Um board com um card nele

Uma instância nova nasce com um único card de exemplo, AGB-1, com título parecido com "Peça para o seu agente pegar esta task". Ele fica em Abertos, com o harness recomendado embaixo do título. Esse card é o alvo do capítulo 2: você não vai encostar o mouse nele de novo.

Tudo o que você acabou de criar está no seu Postgres, no seu disco. Faça dump, faça backup, mova para outra máquina: é seu, e o board não tem opinião sobre onde roda.

06 · quando não sobe

Duas falhas que valem nome

SintomaO que checar
A porta 3000 está ocupada Alguma coisa já serve nela. Pare esse processo, ou mude a porta publicada no docker-compose.yml e use a nova em todo o curso.
O app sobe antes do Postgres É raro e se resolve sozinho: rode docker compose up de novo. As migrações são idempotentes, então a segunda rodada não custa nada.

Checklist do capítulo

  • O Docker está rodando e o docker compose up --build terminou sem erro
  • http://localhost:3000 abre o board
  • A conta admin existe e você consegue entrar de novo depois de recarregar
  • Existe um projeto e você sabe o prefixo de ID dele
  • Os executores que você realmente tem estão marcados
  • O card de exemplo está na coluna Abertos
